核心结论

文档质量在独立开发项目中属于上乘水平——分层清晰、有明确的垂直切片验收标准、并且已经预见了「AI 生成不可控」「两条高风险工作线互相阻塞」这两个真正的坑。但当前最大的风险不是文档质量，而是文档内部的矛盾已经开始决定实现方向：主线任务的保险丝与信号装置存在两条互斥读法，分别写在四份文档里，M1 的退出条件因此无法执行。

同时，M2 垂直切片的范围对单人来说过大（1 km² 开放世界 + 流式加载 + 弓箭战斗 + 2 类敌人 AI + 天气昼夜 + 音频），而真正决定切片成败的 5 个区域里只有 1 个写了场景设计。建议顺序是：先花半天把 4 个矛盾点定死 → 把 M2 砍掉约 40% → 把 AI→Blender 管线整体推迟到切片验证之后。

01

现状快照与文档体系

仓库目前只有 docs/ 与 .git/，没有 .gitignore、LICENSE 或根 README.md。文档本身自成体系，但技术设计文档里的目录结构图停留在三篇文档的时代，已经过期。

已经扎实

  • 七篇文档分层合理，产品 / 架构 / 规范 / 生产 / 计划各归其位
  • 垂直切片有可证伪的验收标准，不是愿望清单
  • 「先灰盒、再接管线」的执行顺序正确识别了两条高风险线的依赖
  • 存档稳定 ID 纪律、生成层 / 人工层分离、AI 输出视为不可信——这三条判断都正确
  • 开放世界密度基线（open-world-design.md:33-42）附带「不应机械铺设」的免责，认知成熟

结构性缺失

  • 松木深林 / 溪谷 / 守林站 / 山脊 四个区域没有任何场景设计
  • 两个世界事件、隐藏地点只有一句话，无落地规范
  • 敌人「林狼」「异常守护者」各只有一段文字，无感知半径 / 攻击窗口 / 仇恨参数
  • 天气、昼夜只有概念，没有实现规范（触发、插值、优先级）
  • 没有术语表：稳定 ID / 区域 ID / Chunk / SceneSpec / manifest 跨文档反复使用却无统一定义
  • 7 篇文档中 5 篇没有版本号，无 changelog、无状态标记

03

P0 深挖：主线流程的两条互斥读法

这不是措辞问题。四份文档各自写出了自洽的流程，但它们要求玩家做不同的事、在不同地点使用同一枚保险丝。按现在的文档去实现，两条路都会漏掉关键内容。

读法 A · 营地闭环first-scene-design.md

来自 :100、:151-160、:259-267，并被 development-plan.md:43 的 M1 退出条件采用。

  1. 营地溪边物资箱拾取保险丝保险丝位于 120×120 m 营地场景内，紧邻玩家
  2. 在营地安装保险丝 → 无线电恢复:149-153
  3. 收到求救信号「……守林站……别走主路……」
  4. 松木深林入口的雾散开，地图标记守林站搜索区域
  5. 主任务切换为「调查失联的守林站」保险丝在此消耗完毕
  6. 玩家离开营地进森林 → 守林站 → 山脊 → 回合营山脊信号装置无人修理
读法 B · 山脊终点game-design.md

来自 :158（第一版结尾）与 :203（验收场景）。

  1. 离开营地进入松木林，途经溪流与山脊地标
  2. 在森林中收集保险丝、燃料、无线电频率记录三样都在路上，不在营地
  3. 找到废弃守林站
  4. 修复山脊信号装置:203 明确写「修复山脊信号装置」
  5. 收到来自禁区内部的回应:158 解锁通往雾林的道路
  6. 安全返回营地结束切片
冲突点：同一枚保险丝在读法 A 里于营地消耗，读法 B 里在森林获取；而 first-scene-design.md 的整段无线电教学（:92-109、:149-162）只在读法 A 下成立——若采纳读法 B，这两节要整段重写。反过来，若采纳读法 A，则 game-design.md:203 的验收场景和 :158 的第一版结尾都要重写。

建议裁决：采用读法 A，但把「山脊信号装置」从切片结局中移除或降级为 M3+ 的内容。理由是读法 A 与已经写得最细的营地场景、与 M1 的退出条件天然吻合，且「营地里收到一声求救」比「走到山腰修一台大机器」更贴合这个游戏的核心体验——森林是主角。同时保留 :158 的「禁区回应」作为切片结尾的钩子而非修复结果：由无线电杂音的片段暗示，而不是由玩家修好一台装置换来。

05

战略取舍：两处值得重新考虑的方向

文档本身已经把执行顺序排对了（M0 游戏 → M1 灰盒 → M2 切片 → M3 管线）。但两个前提假设值得挑战，因为它们决定了一个人能不能做完。

取舍一：AI→Blender 生成器，值不值得为切片投入

管线（technical-design.md:319-447 + content-pipeline.md）要交付：SceneSpec schema、校验器、AI 规划器、7 个 Blender 生成模块、GLB 分块导出、manifest、导入检查器、确定性测试、快照测试、局部重生成。

它的产出物是地形、植被、岩石、河流——而这四样恰好是 Godot 原生就能做的：FastNoiseLite + GridMap + MultiMeshInstance3D 可以在切片规模（1 km²）内零导出、零 manifest、零跨磁盘工具链版本地完成同样效果。

管线真正开始产生回报的时点是 M5（development-plan.md:96-109：第二生态区、复用生产管线），也就是切片验证之后。

  • 建议：切片阶段用 Godot 原生程序化地形 + 手工地标，把 Blender 保留给它真正擅长且不可替代的部分——木屋、发电机、物资棚、守林站这些需要美术造型的 authored 资产。
  • 把 development-plan.md 的 M3 整体后移到 M2 之后，并在 technical-design.md:511-517 已有的判断上再加一句：若切片验证通过且世界规模确认为 4–6 个区域，M3 可直接降级为「Blender 手工地形 + Godot 程序化散布」。
  • 不要让 technical-design.md:319-447 继续扩充。管线文档目前已经 129 行且在切片阶段无法验证任何东西——每写一行都在推迟能跑起来的灰盒。

取舍二：M2 的范围，对单人是否过大

M2 退出条件要求：1080p 接近稳定 60 FPS + Chunk 流式加载 + 弓箭战斗 + 两类敌人 AI + 主任务 + 两个世界事件 + 一个隐藏地点 + 昼夜 + 天气 + 环境音频，首通 20–30 分钟。这是一张完整游戏的功能矩阵，而垂直切片的职责是验证「这个循环好不好玩」，不是预建功能清单。

建议削减

  • 敌人 2 类 → 1 类（林狼群即可，守护者后置）
  • 天气从切片移除，只保留昼夜
  • 1 km² 开放区域 → ~400 m 走廊 + 单场景
  • 流式加载 延后，先用单场景 + 子场景分块
  • 两个世界事件 → 一个

必须保留

  • 第一人称移动 / 视角 / 冲刺 / 跳跃（教学依赖）
  • 弓箭完整链路：瞄准 → 蓄力 → 命中 → 资源消耗
  • 一类敌人 + 完整感知 / 状态机 / 脱战复位
  • 主任务 + 一个世界事件 + 一个隐藏地点
  • 存档 / 读档 + 稳定 ID
  • 昼夜（它同时是美术展示窗口）
  • 一个地标能被不看地图地认出来（核心体验验证）

依据是文档自己的原则：development-plan.md:174「单人开发工作量过大 → 锁定 P0，减少敌人和系统种类」，以及 game-design.md:26「避免繁琐的重度生存数值」。削减后的 M2 仍然能证伪文档里最关键的那个假设——玩家能否只靠地标和声音在森林里找到守林站。

06

里程碑时间线与风险落点

按 development-plan.md 原始范围重建的顺序，标出风险最集中的位置。注意 M2 与 M3 的顺序是对的，但 M2 自身过重、M3 自身过重，两处叠加才是真正的单人开发风险。

  1. M0 · 工程基础低风险

    Godot 工程、输入映射、设置与日志、第一人称原型、自动构建基础、文档规范。这是全项目风险最低、价值最确定的一段。

    退出：Windows 开发构建在全新环境可启动；键鼠移动 / 暂停 / 退出正常；严重错误写日志。
  2. M1 · 灰盒可玩链路P0 阻塞点

    营地 / 树林 / 守林站灰盒、交互、物品、背包、任务、基础存档。这一步是整份计划的地基，但它的退出条件直接依赖第 03 节那条未裁决的物品流——保险丝修哪台设备不定死，M1 无法验收。

    退出：「营地出发—拾取保险丝—修复设备—返回」完整可玩；存读档恢复关键状态；无阻断问题。
  3. M2 · 探索与战斗垂直切片风险最高

    1 km²、Chunk 加载、弓箭 + 两类敌人、主任务 + 两事件 + 隐藏地点、昼夜 + 天气 + 音频。这是风险最集中的一段，同时压着「范围过大」和「四个区域无设计」两个问题。第 05 节的削减建议主要针对这里。

    退出：首次玩家 20–30 分钟完成主线；1080p 接近稳定 60 FPS；Chunk 切换不丢状态。
  4. M3 · 程序化森林管线价值待验证

    SceneSpec / Schema、地形河流植被岩石生成、GLB 分块 + manifest + 预览、导入检查器、局部重生成。排期上已经正确地排在 M2 之后，但它的价值要到 M5 才兑现——见第 05 节取舍一。

    退出：同版本同 seed 同输入产生相同清单；重生成植被不覆盖人工对象；通过几何与预算检查。
  5. M4 · 内容替换与打磨

    灰盒换正式资产、地标与任务整合、UI / 音频 / 可访问性 / 设置、性能与稳定性优化。

    退出：切片通过内部测试；无 P0/P1 缺陷；连续运行 60 分钟无崩溃或严重内存增长。
  6. M5 · 开放世界扩展

    第二生态区、区域间旅行与进度门槛、完整成长 / 制作 / 敌人体系、动态事件工具。管线在此才真正开始回本，届时再决定完整地图规模是合理的。

    退出：新区域可复用生产管线；跨区域存档 / 任务 / 快速旅行稳定。

两个未被列入风险清单的真实风险

  • 「视觉可读性」风险：这个游戏的核心机制是「靠地标和声音辨认方向」。写实植被很容易摧毁地标轮廓——game-design.md:167 自己写下了「保持地标轮廓清晰，不能因写实植被破坏可读性」，但没有对应的验证方法。建议在 M2 之前就做一次剪影测试：纯黑剪影图能否指认守林站与信号塔。
  • 「导航型玩家」风险：整个设计依赖玩家主动阅读地标、具备空间记忆，且愿意在没有 GPS 的世界里自己找路。首次玩家很可能做不到。open-world-design.md:92 提到「辅助模式」但只作为兜底。建议把它做成一等公民：一开始就允许开启「罗盘高亮地标 / 更明显的路面痕迹 / 任务范围提示」，作为可访问性选项而非失败补偿。
