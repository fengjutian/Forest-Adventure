核心结论

代码已经跑到文档前面。上一版报告提出的 10 处跨文档矛盾里，代码用 4 个明确决策回答了 4 个（保险丝修营地无线电、只做弓、只保留生命与体力、切片先做营地），但7 篇文档一处未改——文档正在从「设计依据」退化成「历史记录」。现在最大的风险不是文档质量，而是两套事实同时存在。

M1 是真实完成的：不是「看起来能跑」，而是 105 项断言覆盖了自动加载、输入映射、贴地、三阶段任务链、真实弓箭发射路径、蓄力/命中/弱点、敌人感知、存档写读、版本迁移与备份轮转，整轮约 2 秒。这个测试底座比多数独立项目的第一版都硬。

下一阶段的瓶颈因此不是技术，而是内容与接线：文档要求 20～30 分钟的切片，当前内容约 90 秒；天气、音频、设置、地图、指南针都是「有接口、无接线」；敌人追击逻辑与死亡流程还会在最基础的地方断掉（详见第 04 节）。

这一节的判断

代码替文档做了决定，这在单人项目里是正常且高效的——卡在文档上不动才是问题。但代价是：现在任何人（包括三个月后的你自己）按 docs/ 去实现，都会做出与现有一致的错误。文档需要的不是重写，而是半天时间的一次回写：把 4 个已裁决项改成代码事实，把 6 个未决项标注「M2 未决」。

根 README.md 是唯一跟上了的文档，但也已经落后：它写「冒烟测试 88 项」（实际 105）、「M2 战斗尚未开始」（实际弓与林狼已可玩）。

04

实现层缺陷：会在最基础的地方断掉

只列能在代码或运行日志里直接指认的问题，按「会不会让玩家卡住」排序。P0 = 会让流程中断或状态丢失，P1 = 核心行为与设计不符，P2 = 卫生问题。

级别问题证据与影响
P0 敌人状态不入档 EnemyBase.get_persistent_state() / apply_persistent_state() 写好了，但没有任何调用方：主场景只注册了 current_scene / player / inventory / world 四个存档提供者，changed_objects 回放也只遍历 interactable 分组。结果：读档后被打死的 3 只狼全部复活，而它们掉落的箭矢还带着「已拾取」状态——存档里出现孤儿键。
冒烟日志：对象状态已恢复 {"object":"wolf_01_drop_arrow"} ← 掉落物恢复了，狼本体没有
直接违反 combat-and-progression.md §9「存档加载后已击败的关键敌人状态正确」与 M2 退出条件「Chunk 切换不丢失任务和敌人状态」。
P0 玩家死亡没有出口 player._on_died() 只做两件事：禁用控制、显示鼠标。没有任何死亡 UI、重生、读档或结算。player_died 信号只有一个监听者（玩家自己）。血量归零后游戏进入不可操作、不可恢复的软锁——只有 F9 快速读档能救。而跌落伤害是真实生效的。
P1 林狼实际上不会追人 三处叠加：① SUSPICIOUS → CHASE 要求距离 ≤ attack_range（1.7 m），也就是说看见玩家 24 m 外只会「走过去看看」，走到 1.7 m 才开打；② 放弃追击的条件写成 distance > sight_range + chase_memory，26 m 与 6 s 量纲相加（=32），既不是视觉距离也不是记忆时长；③ 场景里 leash_radius = 34 声明后从未被读取，离家再远也不会返回。
_decide(): if distance <= attack_range: _set_state(CHASE) # 1.7 m 才开始追 elif distance > sight_range + chase_memory: ... # m + s leash_radius = 34.0 # 全文无引用
实际体验：玩家慢慢走进狼的视野，狼会走过来、贴到 1.7 m 内才开始攻击；玩家只要持续移动，狼 3 秒后放弃。目前「能打起来」主要靠听觉分支（冲刺或弓响时直接进 CHASE）。
P1 音频与天气是空壳 WorldAudio 已就绪但 zones: 0——主场景没有挂任何 AudioStreamPlayer；WeatherController.set_weather() 无调用方。这两项恰恰是文档里承载「用声音和天气引导探索」的核心手段（§8.2、§6.4），现在完全不存在。
P1 设置读了但不生效 SettingsManager.field_of_view 与 master_volume 从 settings.cfg 读入后，全工程没有一处使用：相机 FOV 固定 75，音量只在调用 setter 的那一刻生效，启动时不应用。玩家改完重启会静默丢失效果。
P1 探索工具只有道具没有系统 地图（M）、指南针（C）、背包（Tab）三个输入动作已绑定，但全工程没有任何 is_action_pressed 处理；map.tres / compass.tres 定义了却不在初始装备里。核心体验是「靠地标和声音找路」，而复述地图的工具链一环都没接。
P2 每次开火产生一条引擎错误 spawn_arrow() 在节点入树前设置 global_position，Godot 报 Condition "!is_inside_tree()" is true。当前因为父节点是单位变换，箭的实际位置侥幸正确——一旦父节点带偏移（分块、区域根节点），箭就会从错误位置飞出。已改为「先入树、后设位置」，并补了真实发射路径的断言（本报告完成时该修复已提交）。

P2 测试是「一条龙」且顺序耦合 105 项断言跑在同一个场景、同一个进程里：前一个用例把箭矢从 12 加到 15，战斗用例再断言「≥10 支」；战斗用例真的把狼杀了，随后「存档/读档」用例把「狼已死、箭已捡」写进 slot 0。用例之间无法独立运行，失败定位成本会随覆盖增长而上升。

05

架构评价：哪些做法值得守住，哪些会长成债

5,972 行能撑起这些系统，说明结构是对的。真正的问题不在写法，而在几个会随规模放大的结构性选择。

值得守住

  • EventBus + 领域事件：交互物只发事件，任务系统只订阅事件，两边不互相引用。加新任务不需要改交互代码。
  • provider / loader 存档注册制：模块自己声明状态片段，SaveManager 只负责组装与分发，迁移逻辑集中在一处。
  • 确定性的生成链：地形 / 植被 / 营地三个 seed 分开，同 seed 同结果，截图可复现。
  • PropKit 可替换层：灰盒资产全部走程序化网格 + 顶点色材质，正式美术到位后只替换这一个文件。
  • 敌人分层状态机：感知 / 决策 / 动作 / 状态四层分开，子类只覆盖 _perceive / _decide / _steer_direction。加第二种敌人成本很低——前提是先把现有逻辑的阈值修对。
  • 测试先行的习惯：贴地、任务链、存档迁移、弓箭真实发射路径都有断言；这一条在独立开发里最难得。

会长成债

  • 两套事实：脚本注释逐条引用 docs/*.md 的节号，文档却已落后。注释越多，指涉越假。
  • 单场景装配：camp_scene.gd 负责建地形、摆地标、贴地、撒植被、找水面，还持有狼的节点路径。第二个区域会复制这一整套。
  • 「有接口没接线」的系统：天气、音频、设置、地图、指南针都是半成品。它们各自看起来只差一点，合起来是切片范围的一半。
  • 集成式测试：整个游戏场景 + 105 项断言跑一轮 2 秒，现在很划算；等内容翻倍，启动成本会先于覆盖率成为负担。
  • 缺少性能预算：只有「垂直同步 60」，没有帧时间、三角面、实例数上限，也没有自动测量。等 M2 塞进 1 km² 时，没有基线就没有判断依据。
06

完成度与下一步

里程碑按 development-plan.md 原定义评估。M0、M1 可以判定为完成；M2 大约走了三分之一，且缺口集中在内容而非系统。

  1. M0 · 工程基础已完成

    Godot 4.6 工程、输入映射、结构日志、第一人称原型、一键启动与构建脚本、目录规范。退出条件逐条满足，首次运行自动导入的坑也在 run.ps1 里补上了。

    退出：开发构建可启动；键鼠移动 / 暂停 / 退出正常；错误写入 user://logs/game.log。
  2. M1 · 灰盒可玩链路已完成有自动化验证

    营地灰盒、交互、物品、背包、任务、存档全部打通，并且是端到端断言过的，不是「手动点过一遍」。唯一遗留是敌人状态不入档——它不影响 M1 的三步链路，但会阻塞 M2。

    退出：营地出发—拾取保险丝—修复无线电—返回营火可完整游玩；读档恢复关键状态；无阻断问题。
  3. M2 · 探索与战斗垂直切片约 30%

    已做：弓箭完整链路、一类敌人、昼夜、世界生成（1 个区域规模）。未做：1 km² 与分块加载、第二类敌人、两个世界事件、隐藏地点、天气切换、音频、设置菜单、20–30 分钟内容量。

    差距主要是内容：3 个区域、2 个事件、1 个隐藏点、1 类敌人、1 套音频。
  4. M3 · 程序化森林管线未启动

    SceneSpec / Blender / GLB / manifest 全部空白。上一版的建议仍然成立：切片阶段用 Godot 原生程序化（现在已验证可行）就够，管线等 M2 之后再说。

一句话判断

M1 之后最危险的下一步是继续加系统。当前最划算的投入是：把「90 秒」变成「8 分钟」——也就是把 first-scene-design.md 里被跳过的开场、装备拾取、信号事件补上，同时把敌人状态与死亡流程这两个会断掉的地方修掉。这两件事都不需要新系统。
